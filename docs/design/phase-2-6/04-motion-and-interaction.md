# Motion, interaction and illumination

Motion explains state changes; it never drives saving, validation or scheduling. CSS transitions are the default; no Motion/Rive dependency is proposed. [Research rationale](01-design-vision.md) distinguishes library capabilities from a need to install them. The usable interface must work with every duration set to zero.

`standard` easing = `cubic-bezier(.2,0,0,1)`; exits may use `cubic-bezier(.4,0,1,1)`. Tokens in [02](02-design-system.md) and [tokens.json](tokens.json) provide exact defaults within these ranges. Duration is not a save timeout, spinner lifetime or debounce.

## Accessibility and cancellation rules

Effective reduced motion = OS `prefers-reduced-motion: reduce` OR the user's Reduce motion preference. Effective reduced visual effects = OS `prefers-reduced-transparency: reduce` OR the user's Reduce visual effects preference; forced colors also implies solid surfaces. A user preference may add reduction but cannot force motion against an OS reduction. Toggling a reduction cancels current nonessential effects immediately, preserving focus and values.

Use `focus-visible` outlines, including keyboard navigation on menus. Native button/checkbox/radio semantics carry state, not animated icons alone. Do not announce every render or every pointer hover. Save failure and blocking conflict use persistent visible text and an appropriately scoped alert; routine success may use polite status. Avoid live announcements repeating all conflict rows each time the form rerenders.

## Performance and dependency gate

Animate opacity/color and small transforms only; no layout-driven animation of week grids, blur kernels, viewport height, safe-area padding or native fields. Keep at most one translucent navigation layer visible; menus replace rather than stack glass. Profile scrolling and typing on a physical lower-powered iPhone/iPad with effects on/off. Effects that introduce repeated frame stalls or field lag are removed before launch. This is an acceptance test, not a claim that a static spec guarantees a frame rate.

Motion for React would need a separately justified orchestration case that CSS cannot express clearly, bundle/runtime measurement, interruption tests and reduced-motion parity. Rive would require an actual product need for a nonessential illustration and semantic fallback. Neither is justified by the current planner. View Transition API is researched as optional future enhancement, not a dependency or requirement for this redesign. Unsupported browsers show the new state immediately.
